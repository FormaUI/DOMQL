# DOMQL Design v1.0.0-beta.2

The [DOMQL specification](../spec/README.md) is the contract: DOMQL's module, which declares the DOM as Nexo's domain, and the host that carries queries out against a document. This design sets out how this implementation is built to meet it, and the reasons behind the choices that shape it. It describes DOMQL's version `1.0.0-beta.1` on Nexo's definition version 38, as the specification does, and an outline of the C# half, which waits for its design; [the status overview](features-status.md) says where the implementation still differs. [Nexo's design](https://github.com/FormaUI/Nexo/blob/v1.0.0-beta.1/docs/nexo-design.md), at the release DOMQL builds against, sets out how the language and its runtime are built.

## Architecture

DOMQL is Nexo's host. It registers its module in a Nexo registry beside the modules its callers register, binds each query's values through that registry, reads each query's text with its own module supplied as an import, resolves each request through the registry, and evaluates through Nexo's evaluator, giving each evaluation the hooks that record what it reads. Everything that spans evaluations is DOMQL's: waiting for samples, observations and their sessions, watches, snapshots and their change sets, subscriptions, and the lifetimes of executions.

| Part | What it does | Source |
| --- | --- | --- |
| Entry point | Makes query objects from text or a definition, keeps their resolutions, registers modules, and composes the parts below into the public API | `domql.js` |
| Query objects | A request's definition and bindings, through which every operation on it is carried out | `DomqlQuery` |
| The module | DOMQL's declarations, its types with their members within them, its recognition of the DOM's values, the implementations of its members and of its executions, the targets its owned writes hold, and the functions that start its observations, with what a selector reads | `BrowserVocabularyDeclarations`, `BrowserVocabularyImplementations`, `BrowserExecutionImplementations`, `OwnedWrites`, `BrowserObservationImplementations`, `Selectors`, `BrowserModule` |
| Evaluation | Nexo's evaluator under hooks that record what an evaluation reads and hold the sessions that keep it observed | `QueryEvaluator`, `QueryEvaluation` |
| Observations | Sessions on shared observations, each observation started on its first session and stopped with its last, and the mutation observers of DOMQL's own, which a transient measurement drains | `Observations`, `ObservationSession`, `SessionCache`, `MutationObservers` |
| Frames | A window's animation frames, each running the writes module code asks for, then the reads, the evaluations of the watches scheduled by frame among them | `FrameSchedule` |
| Watches | Keeping a result current: scheduling evaluations and delivering each result that differs | `Watch` |
| Host calls | What DOMQL keeps of each host call a module declares: the request it makes, an execution's mode, and its implementation | `DispatchTable` |
| Events and executions | Listening to event sources, raising a handle's events, and running continuous executions | `EventListener`, `EventDispatcher`, `ExecutionHandle` |
| Behaviors | The continuous executions running, each by its module, its name, its owner and its receiver, where the commands and the members of its module find it, the subscriptions to its occurrences, and the observations of the state it offers | `Behaviors` |
| Snapshots | Comparing results, computing and applying change sets, and keeping live state | `SnapshotComparer`, `SnapshotPatcher`, `Provenance`, `LiveState` |

The DOM enters as late as it can. Making and resolving a query read no DOM, so they work in Node.js; code under `src/dom/` reads the window and the document it is given, never a global, and code under `src/snapshots/` reads no DOM at all, only the results and the metadata Nexo records beside them. Dependencies point one way: `dom/` depends on Nexo and `snapshots/`, and `snapshots/` on Nexo alone.

DOMQL's `typeOf` and its types' `isInstance` recognize a node by its `nodeType` and a window by its being its own `window`, never by a global's prototype, so a node of another window is recognized as one of the window a query runs in is. A node holds functions, which data never does, so data that names a `nodeType` is never taken for a node.

## Resolution

A resolution is kept for its definition and for its bindings' resolution key, the types of its bindings and the strings, Booleans and nulls they bind, which can select what a member reads, while Nexo says it is current and while it is among the 16 its definition used most recently, and is released with the definition, so an unchanged query, and every query made from the same text, is resolved once however often it is evaluated. An operation holds the resolution it was made with, so one the cache lets go of costs only a resolution anew for the next query that asks for it; without the bound, an update binding a string it never bound before, as a position does, kept one resolution more for as long as its text was in use, as [D84](decisions.md#d84) records. A text is parsed once through Nexo's cache of parsed texts, so identical texts share one definition and therefore one set of resolutions, whatever their bindings. A query's imports decide what it resolves against, so registering a module changes no resolution's meaning, and Nexo keeps it current; a resolution that a module declaring a `typeOf` may change goes stale, as its `isCurrent` says, and is made again the next time it is carried out. An operation running on it holds the query evaluator, which resolves the request again before it next evaluates or prepares, so a watch goes on evaluating, and a subscription or a once execution prepares again where Nexo refuses to project through its first preparation.

A module loaded on request has its loader kept by its name, for the instance's life, beside the registry it registers into. A load asks the registry for the names it holds and calls a loader only for a module it lacks; a load under way is kept by its name until it settles, so loads asking for one module meanwhile share it, and one that fails leaves nothing behind, so the next asks the loader again. Resolution looks at loaders only where Nexo refuses an import of a module the registry doesn't hold, so a query whose modules are registered pays nothing for them.

The registry belongs to the instance of the library, as the observations do, one set for each window, so two bundles on one page never share a vocabulary, a resolution or an observation, and a query passes between them as its definition and its bindings.

## Sessions

Every observation a query starts is reached through a session, which the query disposes when `evaluateAsync` settles or is canceled, when the watch or the subscription ends, and when an evaluation no longer depends on it. An observation already running for another query is reached through a session of its own, which leaves its lifetime to its other sessions; the last session to be disposed stops it. Equivalent requests share one observation where their type permits it; a request's identity is its type, its target, the arguments its type says belong to it, and the window it belongs to, so two requests that differ in an argument that changes what is observed never share.

- **What a session gives.** A session gives its consumer the change notifications of the observation and, for a maintained observation, its latest sample, until the consumer disposes it. A session whose callback fails is reported and does not keep the others from hearing of a change.
- **Taking over.** A watch's evaluation takes over a session of the evaluations it replaces wherever it would acquire that same observation again, a shared one with the same type, target and arguments, so a session belongs to one evaluation at a time and an observation the watch keeps needing goes on reporting from one evaluation to the next. A subscription does the same from one event to the next, keeping the sessions an evaluation read and disposing the rest.
- **What an evaluation holds.** An evaluation once acquires the observations of the maintained members it reads, whose samples it needs, and holds those of its other members only while it waits, since a complete result needs nothing more observed; a watch holds them all. An event's projection neither waits nor keeps its result current, so it resolves the observations of its maintained members alone and follows no detached receiver. In five paired rounds against the commit before it, that made projecting an event take 52 to 54% less time and allocate 55 to 62% less, whether it read four members or a hundred rows.
- **Disposal.** Disposing an evaluation disposes every session even where one fails to be disposed, and reports each failure to the window's error reporting, as the specification's [errors](../spec/api.md#api-errors) require.

## Watching

A watch evaluates its whole query each time, and its dependencies are what that evaluation read, recorded by the hooks Nexo's evaluator calls around each member's implementation: a branch not taken records nothing, so what a watch observes follows the branches its evaluations take. Evaluating only what changed would save little for the changes lists most often see, as [the status overview](features-status.md#deferred) records.

A refresh that resamples asks each evaluation the watch holds, its last successful one and the failed one after it, to have the maintained observations it still holds take a new sample, and evaluates once every one has arrived, through the refresh's ordinary path. An observation shared with other watches takes one new sample for them all, which each of them is told of as of any report. The `intersection` type takes one by observing its element again: the browser reports a newly observed element after it lays out its next frame, whatever it reported before, and a report it made before and has not delivered is taken first, so it never stands for the new one.

The delayed schedule keeps one timer of the window's, which each invalidation clears and sets again, and which an evaluation, a refresh's among them, and disposal withdraw, as they withdraw a frame's read. A watch reporting on parts compares, after reconciling, the value at each of its paths in the new snapshot with the one in the last it reported: reconciling keeps a part that didn't change the same value, so the comparison is one of identity. A subscription's throttle keeps one timer for its interval and the one event it holds, whose acknowledgment it rejects as a later one replaces it. A watch or a subscription given none of these options tests one field more for each evaluation or event; [D73](decisions.md#d73) records what that measured.

A selector is read for what it tests by `Selectors`, a scan of its text that needs no parse of the grammar: a class for each `.`, an id for each `#`, the name each attribute selector opens with, and what each pseudo-class reads, from a table of the pseudo-classes it knows, any other taken to read every attribute. Strings and escapes are passed over, so a `.` inside `[title=".a"]` reads nothing. The `selector` observation filters its mutation observer by those attributes, so an attribute no selector of the watch tests, as a behavior's own `tabindex`, evaluates nothing again.

## Comparing and patching

The comparer reads what Nexo's [result metadata](https://github.com/FormaUI/Nexo/blob/v1.0.0-beta.1/spec/runtime/evaluation.md#runtime-results) records beside each value: the provenance of each item, the source the earliest projection it descends from read, by which a list is matched where Nexo classifies every item's provenance as a reference, each standing once; the origin of each value, which tells whether a number came from the same branch, operand or property as the number before it; and the tolerance it compares within. A result therefore holds data alone, and a change set never names an element.

The patcher computes the change set that takes one reconciled snapshot to the next, and applies change sets in place to live state. A watch keeps the metadata of the snapshot it holds for the next comparison, so `sourceOf` reads an item's provenance from it, walking the records of the fields and items along the path, and allocates nothing until a caller asks.

Each of the rules below was measured in five paired rounds against the commit before it, on 1,000 and 10,000 shaped rows, as the median change of each round's samples, in the range the rounds gave:

| Rule | Time | Allocation |
| --- | --- | --- |
| A list whose items descend, place by place, from the same sources in both snapshots, as a list that kept its order does, is matched by position. Matching it by reference would pair each item with the one at its own place, so neither the comparer nor the patcher lists its references | Reconciling: −24 to −36%. The change set of one changed row: −83 to −86% | Reconciling: −52 to −61%. The change set of one changed row: −94% |
| The comparer lists an object's field names once for each record Nexo describes them with. Nexo freezes that record and shares it among the objects one object expression builds, through every evaluation of its resolution; the list goes with the record | Reconciling: −21 to −24% | A result that did not change: none allocated. A watch's refresh of 1,000 rows: −6% |
| The patcher writes a part's path only where the part differs, since a part the next result shares with the previous one is unchanged | The change set of one changed row: −33 to −57%; of every row changed: −35 to −40%. Live state: −15 to −19% | One changed row: nearly none. Every row changed: −17 to −19% |
| Applying a change set unescapes only the tokens of a pointer that hold a tilde, and reaches each change's place without copying its path | Live state, every row changed: −25 to −33% | −25% |

## Host calls and their operations

Nexo resolves and evaluates the queries DOMQL gives it; DOMQL decides when those evaluations occur and what the browser does with the inputs a host call prepares. Subscribing, executing once and running continuously are DOMQL's contracts with its callers, so Nexo knows none of them: it knows only that a function is one its host invokes, resolves and prepares the call, and projects the values DOMQL hands back.

DOMQL keeps the rest in a catalog of its own. `domql.createModule` takes each host call's request kind, execution mode and `impl` out of the declaration, wherever it stands, within a type, within an extension or among the module members, and gives Nexo the signature, so the module a caller writes is one object and Nexo never holds an implementation it must not call. Nexo copies each declaration as it creates the module, and keeps a module's types and their members in the order they were declared, so the catalog pairs each copy with what it took out of the declaration by position, and keeps it by the copy, one entry for each type a declaration stands within. An operation reads its query's host call from the resolution, looks its declaration up in the catalog, and refuses the call where the catalog says another operation carries it out. The request kind is declared, never inferred from a missing field, so an execution whose mode is left out is refused as an execution, where an inferred kind would take it silently for an event source. A host call on a receiver of unknown type has no declaration yet, so its candidates, every declaration Nexo finds that takes the call as it is written, say through the catalog what it requests, and candidates that disagree are refused as ambiguous where the call stands, as Nexo refuses declarations that disagree on who invokes them. Preparation, the null rule and the checking of every value an implementation answers stay Nexo's, so a subscription, a once execution and a continuous execution read their receivers, their arguments and their results by the rules a query reads its members by.

### Behaviors and their owners

Each operation makes one environment as it starts, frozen, holding its window, its document and its owner, and gives that object to Nexo as its evaluator's environment and to every implementation of a host call it invokes, so a watch's evaluations, a subscription's source and a continuous execution's start and updates all receive the same one. A continuous execution's handle prepares every update through an evaluator of its own environment, so the members its preparations read receive it too.

`Behaviors`, one for each instance of the library, as the registry is, keeps each running instance of a continuous execution by its module and name, then its owner, then its receiver, each in a map, so two owners' instances on one element, and one owner's on two, are kept apart, and a command finds its behavior's instance in a few lookups. Each receiver keeps its instances in the order they started, so a command reaches the latest. An execution's handle adds its instance as its implementation answers it, moves it once the instance's own `update` accepts another receiver, and takes it out before calling the instance's `dispose`, so no command reaches an instance ending; a map left empty is released with the last instance it held, so a receiver is held only while something runs on it.

A member reading the state a behavior offers is given Nexo with an implementation that wraps its own, adding the instance its environment's owner finds on its receiver, so Nexo calls it as any member. The `behavior` observation is kept beside the instances by the behavior's name and the receiver, its name alone since its identity can hold nothing of a module or an owner; a behavior of one name in two modules, or of two owners, tells both modules' observations, whose members read what changed for their own. An instance tells them as it starts, after its update, on both receivers where it moves, as it ends, and as its `notify` is called.

A subscription to a behavior's event source is kept beside the instances, by the module, the behavior and the source, then its owner and its receiver, and never by an instance, so it hears every instance there and outlives each. `deliver` closes over the instance's entry, whose receiver an update moves, so an occurrence goes to the receiver the instance runs on as it is delivered; the entry is marked ended as the instance ends, before its disposal runs. Delivering copies the receiver's subscriptions before handing the occurrence to the first, so one a handler adds or stops changes who hears the next occurrence, never this one, and joins their acknowledgments with `Promise.all`.

An event listener answers each event's acknowledgment from what its handler did: one promise, already fulfilled, shared by every event a handler applied as it returned, since it holds nothing of the event; a promise of its own only where the handler returned one, or the event waits while the listener starts, kept until it settles so disposal rejects it; and a rejected one, handled as it is made, where the event failed. In five paired rounds against the commit before it, projecting an event measured within the rounds' noise, a median of 111,000 events a second against 106,000 for one read of a panel; an acknowledgment of its own for every event had cost about a tenth.

### Reactions

A subscription with reactions is given, as it starts, what carries them out: a function of the event's projected value that binds each reaction again, its own values beside `event`, and carries it out as `executeAsync` does, for the subscription's owner and window, answering a frozen list of their promises. A query object keeps the values it was given beside the bindings Nexo made of them, so binding again needs nothing of Nexo's, and a reaction is checked to be a query object of the instance's own by its private field, which a stand-in, as a proxy of one, lacks. The event listener carries the reactions out as it projects each event, before it calls the handler or holds the call while it starts, so they run inside the delivery whenever the handler hears of them. A subscription without reactions takes one test of a field more for each event: in five paired rounds against the commit before it, projecting an event and making a small query each measured within noise, their medians from 3% faster to 3% slower.

### Module code and DOMQL's own

What a window's operations share is made at the first that needs it and kept by the window: its observations, its frame schedule, and the tools an environment offers. An operation's environment holds the instance's `domql` and tools that refuse to run while a query is evaluated; an observation's environment holds the same tools unrefused, since an observation starts while a query is evaluated. Whether one is being evaluated is a count `QueryEvaluator` keeps across the instance, raised around each evaluation, preparation and projection, so an evaluation that a member's implementation starts within another counts too.

`FrameSchedule` asks the window for one animation frame at a time, and runs that frame's writes and then its reads; a read a write asks for joins the frame's reads, and anything else asked for while a frame runs waits for the next, so no frame runs without end. A watch scheduled by frame asks for a read, which disposing it withdraws; the frame still runs, and skips it. The `frame` observation asks for a write each frame while it is held, so a watch reading it evaluates in the same frame's reads. In Chromium, averaged over 240 frames in three runs, holding it with nothing reading it cost 0.02 to 0.03 ms a frame, and a watch reading the left edge of each of 1, 100 and 1,000 boxes through it 0.11, 0.33 to 0.34 and 2.1 to 2.2 ms a frame, a result that never changed compared each frame: a module holds it only while a gesture or a pointer needs it, and a watch reading many boxes through it costs a seventh of a frame for each thousand.

`MutationObservers`, one for each instance of the library, makes every mutation observer DOMQL runs, its observations' and its owned writes', and keeps each by its window while it observes. A transient measurement takes the records each of its window's observers holds, adds the class, reads, writes the class attribute back as it was, takes their records again, leaves out the records of that element's class attribute, and hands each observer the rest in a microtask, as the browser would have. It touches each observer of the window twice, so a window running many costs a measurement that many takes.

### Kept functions

Nexo keeps a host call's function arguments open until the prepared call is disposed, so DOMQL disposes each prepared call as what it started ends: a handle the prepared call of the instance running, after the instance's own disposal, since that disposal may still call them, and after an update its instance accepted; an event listener the prepared call its source started with, once the source stops, a call prepared again for projecting keeping none; and a once execution its call as its implementation's answer settles. `QueryEvaluator` wraps each kept function so its calls count among the instance's evaluations, which keeps a member it reads from observing, scheduling or measuring, as any member evaluated by a query is kept.

### Events as `on` delivers them

`on` delivers each event behind a proxy, which answers the members DOMQL reads for an event, as `pointerId`, `types` and `composedPath`, from a table of them, and the event's own property for any other, read from the event itself so the browser's accessors check their own object. Nexo's capture reads only the members the event's type declares, so a member of the table costs nothing for an event whose type lacks it, and a module's event type reads the native event as it always has.

### Owned writes

An owned write's target is kept by `OwnedWrites`, one for each set of the module's implementations, so one instance of the library, as its registry and its observations are: by the element in a weak map, and by a key naming the target within it, as `attribute tabindex` or `class open`, the holders of each target in the order they began, the value the target held before the first, and the value DOMQL last wrote, which it reads back from the element after writing so the browser's serialization decides it. A holder that keeps its value observes its element's attribute with a mutation observer filtered to it, one for the holding, kept through every update that holds the same target and keeps it still, as [D85](decisions.md#d85) records, the `class` and `style` attributes for a class and a style property, and its child list and their text for its text, and writes its value again among the next animation frame's writes, through the environment's `frame`, rather than in the mutation's own microtask, so a frame watch reads the value kept in the frame it was written in. Having written again, it notes the attribute or the text as the other writer left it, from the target's `written`, and asks two frames more of the schedule. A change before the second runs that restores what it noted is an answer: the writer keeps a value of its own, in a microtask or a frame of its own, so the holder yields to it, writing nothing more until its next update, where two writers that each kept a value would alternate once a frame without end. A change that leaves anything else is a patch, a framework rendering the element again, and is undone as the first was. A text target writes the data of the element's one text node, finding the node again at each read and write, so a framework that rendered it keeps it.

## The C# half

This section outlines the C# half, which waits for its design, as [the decisions](decisions.md#d46) record.

The C# half carries a watch to a .NET application, which starts a watch and receives its results; it is a caller that keeps its own copy of each result, as [keeping a copy of a result](../spec/results.md#results-keeping-a-copy) sets out. Its API follows the JavaScript one:

| C# | Meaning |
| --- | --- |
| `Domql.Query(text, bindings)`, `Domql.Query<T>(text, bindings)`, and from a definition alike | Makes a query object, binding its parameters, as `domql.query` does |
| `Domql.TryQuery(…)`, `Domql.TryQuery<T>(…)` | Attempts exactly what `Domql.Query` does, answering false with a diagnostic for a syntax or structure failure |
| `query.Definition` | The query's immutable definition, without its bindings |

C# writes text, and names the type its result maps onto, or none:

```csharp
public sealed record PanelState(double? Width, bool HasFocus);

DomqlQuery<PanelState> typed = Domql.Query<PanelState>(
    """
    panel {
        width = it.size?.width,
        hasFocus = it.focusWithin()
    }
    """,
    ("panel", panel));

DomqlQuery untyped = Domql.Query("panel { size = it.size }", ("panel", panel));
```

A `DomqlQuery<T>` answers a `T`, mapped by its declared contract, which matches the result's fields to the constructor parameters of `T` by name regardless of case, so a field `nearend` fills a parameter `NearEnd`, and reports an ambiguity where two fields differ only in case, since DOMQL itself tells them apart; a `DomqlQuery` answers a `DomqlSnapshot` giving structured access to its values. C# has no C# type standing for each vocabulary concept: a module contributes its declarations and implementations, and the text names what the query reads. `Domql.TryQuery` attempts exactly what `Domql.Query` does, making a query and checking the syntax and the structural rules that need no vocabulary, an empty object expression, a duplicate field and a reserved name among them, without resolving its vocabulary or evaluating anything, so a successful return means the query was made, not that it is ready to be carried out: a syntax or structure failure returns false with a diagnostic, and any other failure is thrown, never swallowed. A vocabulary failure, such as an unknown member, arrives when the query is resolved. C# cancels with a `CancellationToken` where JavaScript takes a `signal`.

Its adapter owns the synchronization:

- **Live state by default.** It watches live state, and takes its baseline from the first ready event's `args.snapshot`.
- **One update at a time.** It queues the immutable changes after the baseline and delivers them in order, sending the next only once the receiving side acknowledges that the one before was applied completely. Acknowledgment follows application alone, never the application's handlers, and a failed delivery stops every further update of that watch.
- **One ordered queue.** Every handle of a connection, its watches' changes and its subscriptions' occurrences alike, sends through one queue, bounded, never coalescing an occurrence, and failing explicitly where it overflows, so the receiving side hears them in the [order](../spec/api.md#api-order-across-handles) the JavaScript side's handlers did.
- **No partial state.** No consumer observes a change set partly applied: access to the C# result during an update follows an explicit rule, a result whose application failed becomes unusable, and the application's handlers are notified once the update is applied.
- **Obsolete watches rejected.** The receiving side rejects a delivery from an obsolete watch before applying it, through a token of its own for the watch it follows.
- **Recovery from uncertainty.** Where applying an update throws, a call rejects, or a call times out leaving its outcome uncertain, the adapter first invalidates the old watch, so its late applications and acknowledgments change neither the replacement result nor the new queue, then disposes it and rebuilds the result from a fresh watch's baseline. Where the connection is lost with the components holding its results, their replacements start watches of their own; where it resumes with them, an update unanswered across the interruption is uncertain and recovered as a timeout is.
- **Handler failures reported, not retried.** An exception from an application handler is reported without restarting synchronization, since the state was already accepted.
- **One way of applying.** Its application of change sets passes a conformance corpus the JavaScript patcher passes too: each case a previous result, a change set and the result they give, reviewed independently of either applier, moves and escaped paths among them.

## Decisions not taken

Each of these was considered, measured where cost decided it, and not adopted. It is reopened only by the need its row names.

Each lands after 1.0 without a break, which [1.0 requires](features-status.md#what-1-0-requires):

- **As an addition,** an option, a method, a member or an event no caller uses today: observing the positions of chosen boxes, `watch.changesSince`, `watch.update`, a subscription delivered by frame, `flushOn`, a handle's event sources, `run({ anchor })`, `runAsync` and a window the viewport decides.
- **Within the implementation,** no result or event changing: one native observer shared by every element, a query object keeping its evaluator and one keeping its resolution. Each changes only how often a member's implementation is called, which [no watch promises](../spec/watches.md#watching-what-an-evaluation-gives).

| Decision | Why not | Reopened by |
| --- | --- | --- |
| Observing every box's position | `rect` keeps its own size, its scroll containers' scrolling, the window's size and its trees' structure, and stays partly observable. Observing its trees' mutations would cost a refresh for each one, about 50 ms for 10,000 rows in Chromium, and still miss a move a stylesheet, an image or a font causes. An intersection observer for each box caught nearly every move, but a watch of shaped rows started 78 to 88% slower and held about 60% more script memory a row, and scrolling 5,000 watched rows took 68 ms a frame rather than 17. | A consumer that needs the moves of a few chosen boxes followed without a refresh, as an opt-in for them |
| One native observer shared by every element | Routing records through one `ResizeObserver` and one `MutationObserver` was correct, but disposed 55 to 111% slower and held 13% more script memory a row. Under `immediate`, one layout change resizing 1,000 rows evaluated a watch twice rather than 1,001 times, at the same disposal and memory cost for every watch of a box. | An implementation whose disposal and memory both cost less, or a workload in which the renderer's memory at that scale matters |
| A minimal change set against an acknowledged result, `watch.changesSince(snapshot)` | Change sets [compose](../spec/results.md#results-composing) by concatenation, each item matched by its source throughout, so a host coalesces them without DOMQL, as [D65](decisions.md#d65) records. A minimal one only bounds a delivery's size, which the latest snapshot sent whole bounds too. Computing one would keep the metadata of every snapshot delivered, and with it the elements its lists came from, as long as the caller holds the snapshot. | A host whose concatenated change sets cost more to deliver and apply than the snapshot sent whole, measured |
| `watch.update` for new bindings | A caller starts a watch of the new bindings and disposes the old one once the new one is ready; every observation both read of the same target and arguments runs on throughout. | A consumer that needs its listeners or its live state's identity kept through new bindings |
| A subscription delivered by frame | Every event is projected in the task it is dispatched in, and a [throttle](../spec/events.md#events-throttling) paces what reaches the handler, keeping the latest, by an interval, as [D73](decisions.md#d73) records. A frame would deliver no event at its dispatch, and its moment and the user's activation with it, while what a frame renders reads the latest value itself, in the frame it renders. | A consumer that needs events paced by animation frames rather than by an interval |
| `flushOn`, a subscription that evaluates a delayed watch at once | `refreshAsync()` evaluates now instead of at the schedule, and a caller's handler of the event that flushes runs inside its dispatch, as [D73](decisions.md#d73) records, so a second way to evaluate now would add nothing. | A caller across a boundary that must flush on an event and can't run a handler in the browser |
| Event sources a continuous execution's handle offers | A handle's events end with its execution, so a caller replacing a behavior would lose what happens between, and could listen only once it runs. A behavior's occurrences go to its module's event sources instead, bound to its owner and its receiver, as [D3](decisions.md#d3) and [D49](decisions.md#d49) record. | A caller that needs an occurrence of one run of a behavior, told apart from another run for the same owner on the same receiver |
| An execution's lifetime anchored to its element, `run({ anchor })` | A watch of `element.attached` disposes the execution in a few lines of its caller's, as the library guide shows, and evaluating by frame keeps an execution whose element a framework moves, removing and inserting it in one task, as [D74](decisions.md#d74) records. Built in, it would hold that same observation for every execution, and decide for every caller how long a move may take. | A caller that anchors many executions, where a watch of each costs more than one shared observation would, measured |
| A continuous execution that waits, `runAsync` | `run` answers synchronously, with the execution started; asynchronous work it began may still be under way. | A caller that needs to know when a continuous execution is ready, beyond its having started |
| A query object keeping the evaluator it was last evaluated once with | Reused while the query resolved to the same resolution in the same window, as a watch reuses one, it made evaluating a small query again take 31.5% less time and allocate 38% less, in seven paired rounds. Reading 1,000 or 10,000 rows once through locals took 4 to 5% longer, beyond the 3% an unchanged copy measures, while reading them shaped did not change. A new query evaluated once took 1.7% longer for the record it kept, and 6% longer where a weak map by the query kept it. Once only a part's path was checked, taking it out made evaluating a small query again 68% slower, allocating twice as much: a small query's evaluator costs about what its evaluation does. | A host whose small queries are evaluated again far more often than large ones are read once, or a Nexo evaluator that costs less to create |
| A query object keeping the resolution it was last resolved to | It would spare reading its bindings' resolution key, which Nexo writes anew at each read, each time the query is carried out. In seven paired rounds, evaluating a small query again measured a median 3% slower, its rounds from 7% faster to 19% slower, within noise, and allocated the same: the key of a few bindings costs little to write. | A query with many bindings, whose resolution key costs more to write |
| A window the viewport decides | `rows.where(it.intersects({ root = panel }))` already answers which rendered rows intersect a panel. It holds an observation for every candidate and selects only rendered rows, so it is no virtualization. | A consumer that needs DOMQL itself to decide which rows are rendered |
